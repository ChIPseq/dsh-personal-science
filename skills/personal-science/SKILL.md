# personal-science 工作约定

这个项目的科研状态在 `sci/`。**默认不自动注入**（每步都注入太重）——需要时自己去看。

## 零、把状态读给用户看：以对话为准，不以命令卡片为准

命令卡片只有**一行**：`> 命令名 · 全文被压成一行并截断`（点开才展开）。所以命令输出不能当作"用户已经看到了"。

1. **用户直接用自然语言问**（"现在到哪了 / 结果文件在哪 / 路径是什么 / inbox 里有什么"）时，**由你自己读、自己答**：读 `sci/STATE.md`、`sci/ledger/<今天>.jsonl`、`inbox/` 与最近产物，然后在回复里给 5-10 行摘要 + 关键路径。不要回答"请运行 /where"——那是把不可见的输出再推给用户一次。
2. 命令执行后会有一条以 `【personal-science · 回执】` 开头的**隐藏上下文**送到你这里（默认 `deliver: pending`，用户看不见它）。它**不是用户输入**：仅作背景，用户问起时再复述，不要主动展开、不要移动或修改任何文件。
3. 每条命令的完整输出在 `sci/out/<命令名>.md`。用户说"看完整清单 / 刚才那条命令的完整内容"时读这个文件，而不是凭记忆复述。

## 一、文件角色（一个文件只有一个角色，角色决定写入方式）

状态不维护就变成噪音：`STATE.md` 的「停在哪里」过期了，下次冷启动就会被带偏。

| 路径 | 角色 | 写入方式 |
|---|---|---|
| `sci/STATE.md` | 当前状态快照，**唯一允许整体重写**的文件 | 重写；保持 <= 45 行 / 1800 字 |
| `sci/log/<日期>.md` | 会话日志 | **只追加**，新内容一律加 `## HH:MM · 标题` 节 |
| `sci/dead-ends.md` | 死路台账 | **只追加**行，不删不改 |
| `sci/ledger/<日期>.jsonl` | 工具调用台账（插件自动写） | 人不要碰 |
| `sci/branches.json` | 分支树（插件自动写 + `/branch` 补方向） | 只通过 `/branch` 写 |
| `sci/out/<命令>.md` | 斜杠命令的完整回执（插件自动写） | 人不要碰 |
| `Plan_Summary/`、`paper/`、`Experiment/` | 分析产物 | 见下 |

**硬规则：任何分析文档、方案文档、论文稿都不允许整体重写。** 要修订就在文件末尾追加 `## YYYY-MM-DD 修订` 节，说明改了什么、为什么改。整体重写会吃掉证据链——一个文件被整体重写 295 次，等于 295 个中间版本全部丢失。

## 二、会话节律

- **开始**：跑 `/where` 看现在；若「下一步」是空的，先把它填成 1-3 个可立刻执行的动作，再动手。
- **中途**：每当得到一个**可判定的结论**（数值、显著性、图、否证），立刻：
  1. 追加到 `sci/log/<日期>.md`；
  2. 更新 `sci/STATE.md` 的「当前判断 / 开放假设 / 下一步」。
- **失败**：任何"试过但不行"的路线，立刻 `/deadend 试过 X，因为 Y 不行（证据：路径）`。不要只在对话里说一句——压缩之后就没了。
- **收尾**：`/wrap`，补上"证实了什么 / 否证了什么 / 下一步"三行。
- **分叉**：准备在新对话里试另一个方向时，先在**当前**会话 `/branch <这个分支要验证什么>`，再到分支会话里继续。分支会话会继承这条方向。

## 三、目录与命名

- 一次实验一个目录：`Experiment/<YYYYMMDD>_<主题>/`，内含 `design.md`（先写设计再写代码）、`scripts/`、`results/`、`logs/`。
- 分析/方案文档：`Plan_Summary/<YYYYMMDD>_<主题>.md`。
- **临时脚本只允许放在 `_scratch/`**，且当天结束前要么提升为 `Experiment/*/scripts/` 里的正式脚本，要么删除。项目根目录不允许出现 `tmp_*.sh` / `tmp_*.py`——那是上下文丢失的化石。
- 数据集、大文件不进 git；脚本、文档、manifest 进 git。

## 四、版本与证据

- 项目根有 git 就每完成一步提交一次（不 push）。没有 git 就先 `git init`——没有版本控制的"长期记忆"是不可信的。
- 引用任何数字时，指向产生它的文件路径；不要引用只在对话里出现过的数字。

## 五、与记忆插件的分工

- `sci/` 是**项目状态**：项目内、可 git、人可读。
- 跨项目的失败模式、方法偏好、领域事实交给记忆插件（`contextual` / `knowledge` 层，带项目标签）。
- 不要把同一份内容抄两遍：`sci/` 存"这个项目现在怎样"，记忆存"我在科研上学会了什么"。

## 六、收件箱（`inbox/`）

用户把想分享的资料（别人发来的调研报告、文献 PDF、数据表、方案）丢进项目根的 `inbox/`。
**只有用户显式要求时才处理**（"处理 inbox"、"分析新放进来的资料"）。平时它只是一块空地，不要主动去翻。

处理流程：

1. **列全**：`/inbox` 或直接列目录，拿到每个文件的真实大小与时间。
2. **读透**：逐个读到"知道它是什么"的程度。
   - PDF 优先 `pdftotext`；没有就用 Python 的 `pypdf`；扫描版/加密读不动的**不要猜**。
   - 读不动的文件留在原地，在回复里列出来说明原因，让用户决定。
3. **判定归属**（按内容，不按扩展名）：
   - 文献 PDF → `papers/pdf/`，并在 `papers/papers.csv` 追加一行（DOI / 年 / 期刊 / 主题）
   - 调研报告 / 综述 / 方案 → 提炼成 `Plan_Summary/<YYYYMMDD>_<主题>.md`，原文放 `reference/`
   - 数据表 → `data/`
   - 脚本 → `Experiment/<YYYYMMDD>_<主题>/scripts/`
   - 图 → `figures/`
   - 拿不准就**留在 inbox 并说明**，不要塞进 `_scratch` 敷衍。
4. **移动而非复制**（复制会留下两份真相，以后必然分叉）。
5. **记账**：`sci/log/<日期>.md` 追加一节，每个文件一行：`原文件名 → 目标路径 → 一句判定理由`。
6. **清空**：处理完 `inbox/` 必须只剩 `README.md` 和 `.gitignore`。若有剩余，在回复里明确说"还剩 N 个，因为 X"。

补充：`inbox/` 自带 `.gitignore`，投进去的东西默认不进 git；正式归档到 `papers/`、`Plan_Summary/` 之后才受版本控制。

## 七、反模式（都真实发生过）

- 把方案文档当工作记忆反复整体重写 → 版本全丢。
- 结论只留在对话里 → 一次压缩就没了。
- 根目录堆 200+ 个 `tmp_*` 脚本 → 事后无法回收，也不知道哪个是最终版。
- 冷启动时靠人粘贴长背景 → 应该由 `sci/STATE.md` 承担。
- 把 `inbox/` 当仓库用（只复制不移动、处理完不清空）→ 同一个文件出现三个版本，谁是最新说不清。
