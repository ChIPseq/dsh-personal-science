# 设计说明：为什么是 0 个工具

## 一、来自真实失败案例的三条证据

对一个月的真实科研工作区（`D:\workspace\ZhangLab-CPU`，32 个 session / 852 turn / 9,840 次工具调用 / 20 次上下文压缩）做会话日志分析后，得到三条结构性失败，而不是"记忆插件没装"：

1. **同一份分析文档被整体重写 295 次**（另一份 199 次）。它同时被当成草稿、结论台账、待办和工作记忆——角色混用导致写入方式只能选"整体重写"，295 个中间版本一个都没留下（项目没有 git）。
2. **20 次上下文压缩**把"为什么放弃某条路线"这类推理抹掉。失败原因只活在对话里。
3. **项目根堆积 200+ 个 `tmp_*.sh`**（`tmp_chk1..23`、`tmp_probe.sh` 重写 36 次），没有"这一步属于哪个实验"的归属，事后无法回收。

结论：缺的不是记录能力（agent 已经在自发维护 `Plan_Summary/`、claims ledger、执行记录），缺的是**角色分离 + 写入规则 + 自动注入**。

## 二、三条设计原则

### 1. 状态要能被"问"，而不是只能被"记"

两个已有的科研插件（`dsh-science`、`dsh-science-workbench`）都靠"模型自觉调用 `research_state` / `bio_get_project`"来维持状态。一旦模型这一轮没调，状态就断——而且模型无从知道自己断了。

修法有两条，v0 选了第一条，v0.2 改成了第二条：

- （v0，已降级为可选）`systemPrompt.context` 在**每次模型步**重新渲染，以 "This snapshot supersedes earlier runtime-context snapshots" 的语义替换旧快照，状态不再依赖模型主动性。
- （v0.2，默认）**人类按需问**：`/where` 一条命令回答"跑到哪了、结果在哪、路径是什么"。便宜、不占 token、不依赖模型。

结论：注入是**冷启动的补丁**，不是日常的主力。见「三点五、v0.2 修正」。

这个 callback 拿不到 agent？——拿得到。`assembleContextFor(agent, signal)` 返回 `{ agent, scope: agent, ... }`，全局注册的 context 对每个 agent 都会收到它（v0.2 起同时接受 `assembly.agent` 与 `assembly.scope`，因为类型声明里只写了 `scope`）。

### 2. 台账要由事件写，不要由模型写

`tools/result` 是 emit 事件，携带 `exec.agent` 与 `exec.arguments`。挂在上面写 JSONL，模型无法"忘记记账"。

代价是记账很粗（只有工具名、签名、成败），但**粗而必有的证据**胜过**细而可漏的证据**。需要精细溯源时，由模型把某次结果"提升"为正式产物——这是后续版本的事。

### 3. opt-in 用目录存在性表达

`<cwd>/sci/` 存在 = 这是科研项目。没有就什么都不做。

这一条是为了让插件可以常驻 profile：代码仓库、临时目录、别人的项目里不会被写入任何东西。

## 三、文件角色与写入规则

| 文件 | 角色 | 写入方式 | 理由 |
|---|---|---|---|
| `sci/STATE.md` | 当前状态快照 | 唯一允许整体重写；<= 45 行 / 1800 字 | `inject=full` 时它会进上下文，必须小且最新 |
| `sci/config.json` | 注入开关 | `/inject` 写 | 让"重不重"由项目自己决定，改完立即生效 |
| `sci/log/<日期>.md` | 会话日志 | 只追加 | 追加 = 天然版本化 |
| `sci/dead-ends.md` | 死路台账 | 只追加 | 失败信息一旦被"整理"就会失真 |
| `sci/ledger/*.jsonl` | 工具台账 | 仅插件写 | 机器事实，人不该编辑 |
| `sci/branches.json` | 分支树 | 仅插件 + `/branch` 写 | 从 session header 还原，人是补语义 |
| `sci/state-history/` | 快照归档 | 仅 `/wrap` 写 | 让"重写"也可追溯 |

**核心规则：分析文档、方案文档、论文稿只允许追加节，不允许整体重写。** 这条写进了 skill，因为它正是 295 次重写的直接成因。

## 三点五、v0.2 修正：默认不注入

v0 的论点是"状态要注入，不要请求"，默认每一步注入完整 STATE（约 500 字）。第一次实跑被否掉了：

> "我好像也不需要，太重，有时只是看任务跑到哪了，结果文件分析，数据保存路径。"

这条反馈把两件事分开了：

| 需求 | 频率 | 正确载体 |
|---|---|---|
| 我做到哪了、结果在哪、路径是什么 | 几乎每次 | **`/where`**（按需、便宜、不占 token） |
| 这个项目的科学判断是什么、哪条路已经死了 | 冷启动 / 换分支 / 长期回归 | `sci/STATE.md` 与 `/resume` |

把第二件事塞进每一步的上下文，等于为低频需求付高频成本。所以 v0.2：

- 默认 `inject: "off"`；
- `brief` 一行（~100 字）、`full` 只在前 2 步给全文然后回落；
- 开关写在 `sci/config.json`，`/inject` 改，**不需要重启**；
- 新增 `/where` 承担高频问题：今日台账尾部、最近产物（按 mtime）、疑似作业命令、关键路径，最后附一行**注入自检**（渲染次数、agent/cwd/sci 是否解析到、错误）。

保留的教训不是"注入错"，而是"**默认值错**"：注入解决的是冷启动失忆，不是日常定位。

### 为什么最终不走 `systemPrompt.context()`

第一次实测：注册不报错，但 `/where` 自检显示 `渲染 0 次`——回调从未被调用。

读 DSH 源码得到原因：`context()` 的实现是

```js
return this.layers.effect(this.ctx, (layer) => layer.contexts.insert(...))
```

`this.ctx` 是 **SystemPrompt 服务实例**所在的上下文，注册落到那个实例自己的作用域层。而 `dsh-web-app` 对 `system-prompt` 这一行有 override（bundle 列表里的 `overrides` 就包含它），于是 bundle 插件绑到一个实例、agent loop 从另一个实例组装——条目录进了没人读的那一层。

改走 `system-prompt/assemble` waterfall：它是 ctx 上的事件，每次组装都会派发给所有监听者，与实例、与层都无关，`context.agent` 也在形参里。插件直接往 `assembly.contexts` 追加一条：

```js
ctx.on('system-prompt/assemble', async (assembly, context, next) => {
  const base = await next()
  return { ...base, contexts: [...base.contexts, { name: 'personal-science-state', text }] }
})
```

代价：这条路径没有"scoped 覆盖 global"语义，也不参与 `order` 排序（追加在末尾）。对一行状态来说无所谓。


## 四、为什么记 branch

DSH 支持"在新对话中分支"：新会话 `isSeeded: true` 且 header 带 `parentSession`。这是科研里最重要的操作之一——岔路口选一个方向试。

原始案例里分支链是 `2d55e43c → 04a9d50d → 00b16915 → b9f5cfaa → ff71a1e3`，但**没有任何地方记录每个分支要验证什么**，一个月后只能靠 session id 猜。

插件在 `agent/created` 时把节点写入 `branches.json`（不需要模型参与），分支的**语义**由 `/branch <一句话>` 补。fork 出来的会话会在每一步的注入里看到"自己是某个会话的分支，方向是 X"。

## 五、与记忆插件的边界

- `sci/` = 项目状态：项目内、可 git、人可读、进上下文。
- 记忆插件 = 个人知识：跨项目、失败模式、方法偏好、领域事实。

两边都不抄对方的内容：`sci/` 回答"这个项目现在怎样"，记忆回答"我在科研上学会了什么"。下一版会让 `/deadend` 同时写一条 `contextual` 记忆（带 project 标签）。

## 六、投放箱：为什么是"一块地 + 一条规则"，不是一个命令

需求是"人把想分享的资料放某处，显式要求时 AI 读、分类、归位、清空"。三种做法里，只有一种是稳的：

| 做法 | 问题 |
|---|---|
| 让 agent 自己找"最近的文件" | 它不知道哪些是"用户想让我看的"，会去翻 `_scratch`、缓存、别人的临时文件 |
| 拖进对话当附件 | 一次性，不进项目；下次会话又没了；大 PDF 吃上下文 |
| **固定的 `inbox/` 目录** | 位置可预言、可拖拽、可 gitignore、可清点 |

关键设计只有三条：

1. **位置可预言**：`<root>/inbox/`（`sci/config.json` 里可改）。人和 agent 都不需要猜。
2. **触发显式**：插件不监视、不自动处理，甚至不把它塞进 prompt。模型只有在你说"处理 inbox"时才知道要动它。理由：这是个**具有破坏性的动作**（移动文件），不该被自动触发。
3. **处理完必须空**：这是唯一可机器验证的验收标准。`/inbox` 空 = 处理完了；非空 = 还有东西没归类，或者读不动被留下了。

刻意没做自动分类：扩展名只能猜个大概（`.pdf` 既可能是文献也可能是别人的报告），真正的归属要看内容，那只有读过才能定。所以插件只提供**建议归属**（打印给你和模型看），移动由模型读完再执行，并在 `sci/log` 记一行理由。

也没做"自动清空"：如果模型读不懂某个文件，它必须留在原地并说出来——**静默丢弃比不清空更糟**。

## 六点五、v0.3.1 修正：命令卡片不可靠，回执改走对话

第四次被实测推翻的假设，是"命令的 `result.text` 会显示给人看"。

事实（minisugar 会话，11:08–11:10）：`/resume`、`/inbox`、`/inbox 查看并处理` 三次都执行成功，`command/run`/`command/done` 带着完整文本落盘（seq 9–14），投影缓存推进到 seq 14；界面上**一条都没出现**，刷新也没有。`/resume` 到底做了没有，用户是靠资源管理器里多出来的 `sci/` 判断的。

之前那版曾把同样的现象解释成"瞬时返回太快、客户端还没画出行"（`/inject` 立刻返回不显示，`/where` 扫目录显示），并加了 80ms 延后。**这个解释是错的**：`/inbox` 带了 80ms 依然不显示。延后保留（无害，且如果客户端将来修好，只多花一个 tick），但不再是交付手段。

现在结果走两条**都不依赖卡片**的路：

1. `sci/out/<命令>.md` —— 全文先落盘。任何 UI 都坏了也不影响这一条；可 git、可 grep、可事后回看。
2. 一行 `【personal-science · 回执】` 投进对话：`agent.steer()`（`deliver: "turn"`，默认）或 `agent.inject()`（`deliver: "pending"`，不额外调用模型）。

为什么 `source.kind` 必须是 `user`：Chat 客户端把 `user/message` 里非 `user` 来源一律归类成 `context` 节点，而 `context` 只有当它携带 tool-addition/tool-removal 块时才可见（`chat-visibility`）。换句话说，**除了真正的 user 行，没有第二种能承载任意文本且一定可见的行**。回执因此伪装成 user 行，但带固定前缀，并在 skill 里约束模型"只做一句话确认，不要重复罗列、不要动手"。

这也顺手改了产品口径：**读状态不再依赖命令**。用户直接问"现在到哪了 / 结果在哪"，模型自己读 `sci/` 和 `inbox/` 再回答——这条路径既可见又没有额外成本，命令退化成确定性的快捷方式。

### v0.3.2 追加修正：卡片其实渲染了，只是只有一行

重启后再看，命令并没有"消失"——它们渲染成 `> 命令名 · 全文压成一行…` 的折叠行（点开才展开为 `<pre>`）。所以 v0.3.1 的判断要再修一次：

- 之前"什么都没有"，一部分是无它（折叠行太细，且第一次会话里没有后续 turn 触发重建，确实看不到）；但**卡片本身是有的**，只是不可读。
- v0.3.1 引入的 `turn` 模式把回执做成 user 气泡，结果是**伪造了一条用户发言**：截图里它和真正的用户消息（同样的浅蓝右对齐气泡）完全分不出来。这是比"看不见"更糟的错——用户无法区分自己说过什么。

因此默认改为 `pending`：回执用 `source.kind: "personal-science"` 投进 inbox，客户端把它归为隐藏 `context` 行，用户界面干净；模型在下一步收到它（`user/message` 仍进请求），既不多花一次调用，也不会被当成用户在说话。`turn` 保留为显式选项（确实需要"立刻看见"时用），`off` 用于完全不打扰。

一个仍未验证的点：折叠行在**没有后续 turn** 的会话里是否出现。v0.3.1 的回执恰好每次都开了 turn，所以"卡片需要 turn 才会被重绘"这个解释既没被证实也没被推翻。如果以后在干净会话里跑命令又看不到那一行，那才是客户端的真 bug。

## 七、已知取舍（v0 不做）

- 不做 UI。Client bundle 是 80% 工作量换 20% 收益，等 dogfood 出真需求。
- 不做远程作业管理。`pwsh` + `ssh` 原生能力足够；台账会自动记录提交命令。
- 不做文献库/引文管理。先把"状态不断线"这件事做对。
- 不做语义检索的死路匹配。STATE 里已有 top-3 摘要，关键词命中留给 v0.2。
